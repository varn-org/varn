# Varn — project guide for AI Agents

Varn is Lua everywhere: the whole application is written once in Lua and runs on a fast C++ core that behaves the same on desktop, mobile, and the browser (WebAssembly). The C++ `modules/` expose native capabilities to Lua via `require`. The higher-level Lua libraries built on top of them live in their own repository, [varn-org/components](https://github.com/varn-org/components).

This file is binding. Follow it exactly instead of re-deriving conventions each session.

## Core principles (non-negotiable)

- **Production-grade C++ engineering — no shortcuts or technical debt.** Fix root causes, not symptoms. No hacks, kludges, makeshift workarounds, temporary patches, placeholder implementations, fallback code paths, silent degradation, dead code, obsolete or legacy code, or backward-compatibility shims. Remove superseded implementations completely instead of retaining parallel code paths. Prefer the simplest correct, maintainable solution over unnecessary complexity or abstractions. Write idiomatic modern C++ following the project's language standard, architecture, and conventions, with clear ownership, RAII, type safety, proper resource management, and explicit error handling. Never mask failures or silently substitute behavior. Deliver complete, production-ready implementations, and validate changes through builds, relevant tests, and static analysis where available. Do not claim verification that was not performed.
- **No `else` for unknown cases that create surprising implicit behavior.** Handle the known cases explicitly. Do not paper over the unknown.
- **Code and comments are in English.**
- **Every sentence of any text starts with a capital letter** — log messages, console and command line output, error messages, comments, documentation and commits alike. When what would open the sentence is essentially lowercase (a command, an identifier, a flag, a path), keep its exact spelling and put a capitalized word before it instead of starting on it. Write `error: Name the device with --device. Use the command "xcrun devicectl list devices" to list them.`, never `error: Name the device with --device. xcrun devicectl list devices lists them.`
- **A reserved expression is always set apart from the prose around it.** A command, identifier, flag, path or literal value is marked (double quotes in log, console and error messages, backticks in Markdown and comments) and introduced by what it is ("the command", "the flag", "the file"), so a reader never has to guess where the sentence ends and the expression begins.
- **A message names no class.** An error, log or console message says in a sentence what failed, without a tag of the class, module or driver that raised it, since the apps that show it and the people who read it know none of them. A reason that comes from a platform or a library, such as a system error or the failure of a browser fetch, sits inside a sentence that says what could not be done.
- **This file records a number only when the rule depends on it.** A version or value that is secondary to a rule stays out, such as the project version, a dependency or database version, a count of targets or workflows, or a default limit. Name the thing and where it lives (the file, the constant, the option) instead, so the rule stays true when the value moves. A number that is itself the rule belongs here, such as the language standard the code is written against or the minimum version of something essential the project requires.
- **Do the work only when it genuinely makes sense and is actually needed — never just to show work.**
- **The repository keeps a single commit on `main`.** A change amends that commit and is force pushed together with everything else in the working tree, so the history stays one commit with one CI run, and the version tag and its release move to the amended commit with the same version.
- **Nothing opens a pull request on its own.** No bot, workflow, dependency updater or agent opens one, and no workflow or configuration of the repository may. A change reaches `main` as the one amended commit, and a pull request exists only when a person opens it by hand.
- **Branches and commits follow the market convention.** A branch is a type prefix plus a short dash-separated name, never underscores (`feature/http-retry`, `bug/ws-close-race`, `chore/ci-cache`, `docs/embedding-guide`, `refactor/task-pool`). A commit message is the conventional prefix plus a very short, objective subject (`feat: add http retry`, `fix: close race in ws send`). No `Co-Authored-By` trailer, no generated-by line, nothing else.
- **Names use dashes, never underscores.** A file, a folder, a CMake target, a build output and anything else that is named takes dashes (`socket-tls-test.cpp`, `varn-core`, `varn-wasm.js`). An underscore stays only where it is mandatory: an identifier of code (C, C++, Lua, JavaScript, Kotlin), a CMake variable, a macro, an environment variable, a Python module that is imported (`asgi_server.py`, `__init__.py`), an Android resource, and a name a platform or a third party fixes, such as the folder `.github/ISSUE_TEMPLATE`, the system headers `alloca.h` and `dlfcn.h` that the MSVC shims stand in for, and the file `CPM_<version>.cmake` of CPM.
- Build with `cmake --build build -j 4` (this machine can freeze with all cores).

## Commands

Everything goes through `python3 varn.py <task>`:

- `build` — Build the native `varn` executable (then `./build/bin/varn script.lua` runs a script).
- `test` — Run the cross-platform Lua suite (`modules/*/lua/tests/*.lua`, auto-discovered), each test gets a fresh `VARN_TEST_DIR` and the time limit of `--timeout` (seconds per test).
- `test-cpp` — Build and run the googletest C++ targets, `varn-scheduler-tests` and `varn-tests`.
- `format` — Run `clang-format` over `modules/` and `src/`.
- **Sanitizers** — The tasks `build` and `test` both take `--build-dir`, and the build takes `-D VARN_SANITIZE=<list>`, so the whole Lua suite runs instrumented: `python3 varn.py build --build-dir build/asan --config RelWithDebInfo -D VARN_SANITIZE=address,undefined` then `python3 varn.py test --build-dir build/asan` (swap `thread` for a race hunt). Run both before declaring a runtime or networking change safe.
- `wasm` / `app-wasm` / `serve` / `site-deploy` — Build the wasm engine, bundle the browser app, dev server, publish the site.
- `lib` — Build the embeddable `varn` shared library (`find_package(varn)` package). The command `lib --prefix <dir> --install` installs the `varn` component into a clean prefix.
- Every task takes `--jobs N` (four by default) and exports it as `CMAKE_BUILD_PARALLEL_LEVEL`.
- Run a single Lua test directly: `./build/bin/varn modules/<mod>/lua/tests/<name>-test.lua` (set `VARN_TEST_DIR` to a scratch dir).

## Architecture and organization

- **Modules** (`modules/<name>/`) are independent C++ units exposed to Lua through `require("<name>")`. Layout per module: `include/varn/<name>/` (public headers), `src/` (impl), `src/drivers/<driver>/` (swappable backends), `lua/tests/`, `README.md`, `<name>.cmake`.
- **Drivers** are backends selected at build time (e.g. `poco`, `std`, `openssl`, `portable`, `apple`, `android`, `emscripten-fetch`, `dummy`). The `dummy` driver throws `"... not available in this build"`, and the `external` driver compiles the sources that the host names in `VARN_<MODULE>_DRIVER_SOURCES` against the public header of the module, which every driver implements. The event loop has the drivers `libuv` and `pump`, whose host pumps the loop from its own run loop, which the browser and ports without libuv take, so the core names the pumped loop, never the browser. The worker pools follow `VARN_THREADS` alone, on threads of their own with either loop, and only a build without threads, such as the browser, runs their jobs inside the pump. Work that the host completes outside the queue of the loop, such as a fetch of the browser, is counted with `HostWork::begin` and `HostWork::end`, and every poll reports it as pending. A driver option is declared once with `varn_driver_option`, which keeps its default, its help and the drivers it allows together. Keep all drivers of a module consistent in behavior and signatures.
- **A redirect is followed above the drivers, never inside one.** A platform transport follows one itself and each driver blocks it precisely so every target agrees, so `HttpRedirects` does the following once for all of them. A caller chooses with `redirect` (`follow`, `manual`, `error`) and `maxRedirects`, defaulting to follow with the hop limit the fetch standard settled on and most clients took. The method and body rules are that standard's: a `303`, and a `301` or `302` on anything but `GET`/`HEAD`, become a `GET` with no body, while `307` and `308` keep both. Credentials are dropped on a cross-origin hop. Every hop is held to the rules of `HttpClient::refusal`, an `http` or `https` URL of valid UTF-8 with headers of valid UTF-8, so no driver checks a scheme or an encoding of its own. Under wasm the browser follows on its own and cannot report the hop, so anything but `follow` is refused rather than silently answered with the final response.
- **The mobile targets talk to the network through the platform.** The setting `VARN_TARGET=apple` forces the http client onto `NSURLSession` and `VARN_TARGET=android` onto `HttpURLConnection`, so an app's `Info.plist` and `network_security_config.xml` govern App Transport Security, trust anchors, certificate pinning and the cleartext policy, and the trust store, system proxy and HTTP/2 come from the OS. A platform transport follows a redirect and decompresses a body on its own, so the driver blocks the redirect and drops `content-encoding`/`content-length` to keep the Lua-facing contract identical across every target, and the browser driver drops the same two headers. The Android driver resolves its Java classes in `JNI_OnLoad` because a pool thread attached later only sees the bootstrap classloader.
- **The HTTP client is one C++ API that every caller goes through.** The class `varn::http::client::HttpClient` (`modules/http/include/varn/http/HttpClient.h`) sends a request on every target and streams its head and its body to callbacks on the loop, and the functions of `http.client` are built on it. Each request is a transfer (`HttpClientTransfer`) that owns the one deadline as a timer of the loop, so the deadline holds whatever the transport waits for, and that hands the loop at most a bounded window of body the callbacks have not taken, so a host that stops polling stops the download instead of gathering it in memory. A transport on a pool thread waits for room inside `deliver`, which on Apple platforms holds the delegate queue of the session, since suspending a task that already receives does not stop it, so a transfer whose caller releases its own chunks runs on a session of its own there, while the browser pauses its reader. A cancel from any thread interrupts the transport where it waits, the socket on the desktop, which the exchange arms before the connect so the TLS handshake and the request stop too, through a descriptor of its own on POSIX systems that it closes only after it cleared the interrupt (only the reading side on Linux, where shutting the sending side down raises a signal) and through the socket itself on Windows, where a shutdown through a duplicate leaves the connection open, the task on Apple, the connection on Android and the `AbortController` in the browser, and no callback runs after the completion.
- **A client keeps its connections per origin on every driver.** The desktop keeps a bounded pool of idle `HTTPClientSession`s that drops one the server closed or that idled too long, and sends a request again on a new connection only when a pooled one failed before it answered and the request can be repeated. Apple shares one `NSURLSession` per verification mode, so a connection trusted without verification never carries a request that asked for it, and a transfer whose caller releases its own chunks gets a session of its own, so its wait for room never holds the others. Android leaves the pool to the platform and disconnects only a connection whose body was not read to its end.
- **The core is two libraries.** The static library `varn-runtime` holds what needs no Lua: the scheduler, the log with its backend, data views with their tokens and their classes for Objective-C, Swift, Java and Kotlin, the C++ HTTP client with its transports, and TLS. The static library `varn-core` holds the Lua runtime, the Lua engine and every module, and links `varn-runtime`. Each list file of a module puts its sources in `VARN_RUNTIME_SOURCES` or `VARN_CORE_SOURCES`, and only `varn-core` links the Lua interpreter and the header `lua.hpp`, so no source of `varn-runtime` can include a header of Lua, and a C++ program that links only `varn-runtime` links no Lua. The test target `varn-scheduler-tests` (`tests/scheduler/`) links only `varn-runtime` and proves it on every build of the tests. The shared libraries of the targets `apple` and `lib` compile both lists into one library.
- **Scheduler** (`modules/core/.../runtime/Scheduler`): One `EventLoop`, two `TaskPool`s — `taskPool()` (CPU work, limited to the cores) and `ioPool()` (blocking waits, limited by `kIoThreads` in `Scheduler.cpp`, high because its threads mostly wait) — and the `WorkLedger` of the work in flight, whose pool limits the host sets through `Scheduler::Options` (`varn_runtime_new_with_options` in the C API), where a limit left at zero keeps the default. The scheduler holds no Lua. It advances under `poll()` and `poll(budget)`, which drain the pools inside the pump in a build without threads, and `stop()` waits for the jobs that run and drops the ones still queued. The Lua runtime `varn::runtime::Runtime(Scheduler&, args, scriptArgIndex)` holds the `lua_State` and its modules on a scheduler that the host created first and that outlives it, reaches the loop and the pools through `scheduler()`, and stops its scheduler when it stops, since the jobs of the loop and the pools may hold Lua values. The C API, the command line and the browser create a scheduler and a Lua runtime on it together. A pool is elastic: it starts no thread before its first job, starts one only when no worker is idle or already starting and the limit allows it, and a worker idle for `kWorkerKeepAlive` retires, so an idle scheduler holds no worker thread and a slow wait never starves the jobs behind it. Blocking work runs on a pool and resolves a `Promise` on the event loop, and so does CPU work that costs more than a frame, such as a password hash or a key derivation, which never runs on the loop thread. Use `varn::async::AsyncTask::runOnPool(...)` for that pattern. The module `async` exposes `sleep`, `spawn`, `run`, `promise`, `deferred` plus combinators (`all`, `allSettled`, `race`, `any`, `timeout`, `mapLimit`).
- **Runtime invariants (binding):**
  - **Waking costs a system call, so it happens only when it changes something.** A post to a pool signals a worker only when one is idle and no signal is already on its way to one, and a worker that takes a job passes the signal on while jobs remain, or starts the next worker when none is idle, so a burst of posts from the loop thread costs it one signal or one thread start. The `WorkLedger` notifies only when its last entry leaves, which is the one change that can let an idle loop exit, the loop thread never wakes itself since it checks its state again before it waits, a promise that settles while nothing awaits it posts no resume unless it is a rejection no one observed yet, and the loop runs a pass of libuv only while a socket is watched or waits for its close callback, since an empty poll still costs a system call that macOS makes far slower than one that returns a ready event. The tests in `tests/scheduler/task-pool-test.cpp` and `tests/cpp/runtime-pools-test.cpp` guard this under the thread sanitizer.
  - **A post to a pool allocates nothing once the backlog fits.** The pool keeps each job as it came in a ring that grows to the longest backlog and keeps its room, so a host that posts jobs whose functions hold their captures inline, as a job system of a game does every frame, allocates nothing per job. The test `TaskPool.PostingAJobThatFitsAllocatesNothingOnceTheBacklogFits` guards this.
  - A job posted to the loop or a pool must never let an exception escape its boundary — `EventLoop::post`/`postDelayed` wrap the work and `TaskPool::runJob` runs every job of a pool inside a guard, so an escaping throw cannot `std::terminate` the process and the `WorkLedger` entry is always released, and `Log::failure` names the failure in the log, as it does for a socket handler of the loop and for every failure the C API catches, whose poll answers `3` then.
  - **A TLS socket of the `socket` module runs on the loop thread.** The class `TlsSession` runs OpenSSL over buffers in memory and `TlsStream` moves its ciphertext over the plain socket the loop already watches, so the `SSL` object is only ever touched on the loop thread, a receive and a send are in flight at once, no thread waits on the peer, and every platform behaves the same, Windows reading its trusted roots from the system store. A send settles once its ciphertext left for the socket, and a peer that ends the stream without ending the TLS session fails the receive, since that end could cut a message short.
  - **A secure HTTP server ends the TLS session before it closes.** A connection that closes after its response or a WebSocket close sends its close_notify alert first, and when the socket has no room for it, which Windows reports whenever the last record took it past its limit, it waits for the socket to be writable and sends it then, through the patch `cmake/patches/poco-close-notify.patch`, since a non-blocking socket of Poco marks the alert sent even when it did not leave. The stale sweep bounds that wait. The tests `TlsServerSocket.ASessionEndThatDidNotFitLeavesOnTheNextShutdown` and `SocketTls.ALargeBodyArrivesWhole` guard this.
  - Loop-owned state reachable from the cross-thread public C API is mutex-guarded, since `Runtime::stop()` can be called from another thread while the loop runs — this covers the `Runtime` server list.
  - The `EventLoop` outlives the `LuaEngine` by declaration order, so its socket watchers must be released **before** the `lua_State` closes — `~Runtime` calls `EventLoop::shutdownIo()` for the paths where `loop.run()` is never entered (a script that fails, an async entry that fails, an entry that requests stop), since an armed accept watcher holds registry refs and `AppState::~AppState` would unref into a closed state.
  - **The registry is touched only on the loop thread.** A Lua function a request calls later is a `HttpClientLuaFunction`, whose last owner may be a thread of a transport or of a pool, such as the job that moves a downloaded file, so its destructor posts the release of the reference to the loop instead of calling `luaL_unref` where it runs. The test `HttpClientTest.ALuaCallbackDroppedOnAnotherThreadIsReleasedOnTheLoop` guards this.
  - Nothing reached from a cross-thread `Runtime::stop()` may touch the `lua_State` — a destructor that releases a Lua registry ref checks `Runtime::stopped()` first and skips, since `lua_close` reclaims the whole registry anyway (see `HandlerReference` in `HttpServerModule`, `AppState` in `HttpAppModule` and the `refHolder` in `AsyncModule`).
  - **A server closes from Lua as well as with the runtime.** The method `listen` answers a `Server` whose `close` stops the listener, ends every connection (WebSockets with `1001`), at once or once the requests in flight finished and at the latest at its deadline, and then removes the server from `Runtime::servers` through the loop so the loop can end, while collecting the `Server` value closes nothing. A listener binds its port alone, with `SO_REUSEADDR` on POSIX and `SO_EXCLUSIVEADDRUSE` on Windows, and shares it only with `reusePort`, which only the worker processes of `VARN_WORKERS` turn on by themselves, so a busy port fails instead of silently splitting the connections of another server.
  - A socket handler can run after its connection closed, since `Poller::closeNow` runs the pending handlers so their promises settle, so the connection checks that it is closed before it reads, writes or arms another watcher. A watcher armed on a closed descriptor crashes inside libuv.
  - Every option table a server function reads (`listen`, `server:close`, `app:ws`, `conn:send`), the requests of `http.client` and the calls of the `socket` module refuses a name it does not know and a value of the wrong type or out of range, naming the option, so a misspelled limit never passes silently.
  - Reading an untrusted path into memory rejects non-regular files (`FsStorage::readAll`) so an endless stream like a device or fifo cannot loop forever.
  - Lua chunks are always loaded text-only (`luaL_loadfilex`/`luaL_loadbufferx` with mode `"t"`) — never enable bytecode loading, since the wasm host runs source supplied by the page.
  - Network output buffers (the WebSocket send queue, streamed responses) are bounded and the connection is dropped when a peer stops draining — never buffer outbound data without a limit. The cap is measured against the **outstanding backlog**, never cumulative traffic, and the one queue a connection keeps for its responses and its WebSocket frames releases each buffer once it is sent, so a busy but healthy peer is never dropped and a partial drain cannot grow the buffer without bound. The WebSocket cap (`maxQueuedBytes`) counts payload bytes, never the heads of the frames, so a message of exactly the cap still fits an empty queue. A socket of the `socket` module counts the bytes its sends have not yet handed to the system and rejects a send that would pass its `maxQueuedBytes`, so sends that nobody awaits cannot grow without bound either. A UDP socket counts the datagrams its sends have not yet handed to the system the same way. A streamed write, an event-stream send and a WebSocket send settle their promise only once their bytes left for the socket, so a handler that awaits its writes is held by a client that stops reading.
  - Captured child-process output is bounded and a child that overruns the cap is killed, so `process.exec` on an endless producer cannot exhaust host memory. A child may also carry `timeoutMs`, a whole number of milliseconds whose deadline covers the whole run, a child that closed its output included, which kills the child and everything it started at the deadline and **rejects** rather than resolving a partial result — each `exec` holds one `ioPool` thread for its whole run, which the elastic pool absorbs by starting another worker for the jobs behind it.
  - The worker supervisor restarts a worker only on an abnormal exit and backs off a crash loop on every platform, so a fast-failing child can never become a fork storm, and it refuses a `VARN_WORKERS` value that is not a whole number within the bound of `App::workerCount`.
  - **A connection of the HTTP server has one reader at a time.** Arming a reader supersedes the one before it, and while a request is answered that reader only buffers a bounded part of what follows it, so a pipelined request is never dispatched twice or lost.
  - **Never iterate a container while the loop body can run Lua or a user callback** — that callback can register a handler or close a connection, which reallocates or erases out from under the iterator. Snapshot first (copy the refs, or lock the `weak_ptr`s into a local vector) and walk the snapshot, the way `luaEmit`, the request/response/start hook loops and `wsBroadcast` do. The same holds for a pointer or a reference into such a container, which is never read after a call that runs Lua, the way `HttpApp::handleWebSocketUpgrade` copies the refs of its route before the open handler runs. Three remotely triggerable use-after-frees came from missing this.
  - Caller text written into a line-oriented protocol frame is escaped when it is content and refused when it is structure — an SSE payload is split so every CR, LF and CRLF opens a new `data:` field, while an event name or comment, which owns its whole line, raises on a line break the way an invalid header name does. Escaping one field and forgetting its neighbour is how forged records reach a client.
  - A cost or size parameter read back out of stored data (the `N,r,p` of a `scrypt$` hash, a declared length, a window) is validated against a ceiling **before** it is handed to the primitive that allocates for it, and it is range-checked on its full parsed width so a narrowing cast cannot turn an absurd value into an accepted one. An unvalidated cost is a remote kill, not a slow path.
  - Every store keyed by something a client controls is bounded, and the bound is enforced where the entry is added — the session store by `maxSessions` with eviction, the rate-limit store by `maxClients` with a sweep and a reset. An IPv6 peer can source from a whole prefix, so a per-address map with no cap is an unbounded allocation, not a cache.
  - A host event crosses into Lua only through the loop. The function `Runtime::emitHostEvent` posts the delivery rather than calling in place, skips when `stopped()`, and copies the handler list before invoking any of it, since a handler may subscribe another one.
  - Worker processes share nothing. Anything a handler keeps in memory (sessions, the CSRF secret, rate-limit counters) is private to one worker, so a feature that depends on cross-request state either says so loudly at runtime or lives in a shared store.
  - **A host drives the runtime one of two ways, and both are first-class.** The functions `run_file`/`run_string` take the thread until the loop is idle, which is what a command-line program wants, and a build with the pumped loop refuses them before the chunk runs, since its loop runs only under the polls of its host. The functions `load_file`/`load_string` plus `poll` let the platform keep its own run loop, which is what a user interface needs, since every `host.<name>` call then lands on the thread that pumps and a UI bridge touches its widgets with no dispatch and no deadlock. Under wasm `poll` must also drain both task pools, because the browser has no threads and a pool job only ever runs when the pump drains it, and a job a pass posted to a pool counts as pending work. A budgeted poll drains them one job at a time and stops at its budget, so a long run of pool jobs never holds a frame.
  - **The loop runs in passes.** A pass runs the jobs queued and the timers due when it starts and then serves every ready socket, so work armed during a pass waits for the next one. The function `varn_runtime_poll_budget` (`Scheduler::poll(budget)`) repeats passes while they make progress and the budget lasts and checks the budget between jobs, which is what keeps tasks that wake every frame from holding a frame forever, while the plain `poll` runs every pass of work there is and then one pass over the sockets. A socket handler that completes lets the next waiting handler of that socket run in the same readiness, up to a bound, so an accept checks that a connection waits before it accepts.
  - **A host that polls sleeps until the runtime has work.** The function `varn_runtime_idle` answers the time to the next timer, zero while a job waits and minus one when only another thread can bring work, and the wake function a host gives `varn_runtime_set_wake` is called from every post that arrives from another thread, under a mutex that `set_wake` takes too, so clearing it returns only once no call is still running. A watched socket is read only when polled, so it bounds the idle answer to fifty milliseconds. In the browser the wake is called for a post a callback of the page makes while no poll runs, such as the end of a fetch, and for every change that can let the loop end, such as the end of a fetch that a cancel or a deadline already settled, since a fetch in flight counts as pending work, which is how `varnRunChunk` sleeps between its slices.
  - A settled promise never changes its outcome, so every awaiter reads it in place instead of a copy, a long string becomes one Lua string all of them share, and that string is released through the loop, since the last owner of a promise may be a pool thread.
  - A streamed HTTP request settles through the loop, behind the head and the chunks it already posted there, so a caller that awaits it late never sees it end before them.
  - A subscription made with `host.on` does **not** hold the loop open. A timer will fire and a socket has a peer, but an event may never arrive, so keeping a process alive forever for one is wrong — this matches Node, where a listener does not keep the process running and only a handle does. A host that wants to wait says so with `varn_runtime_retain`.
  - **The thread of a chunk is the loop thread from its first line.** The function `Runtime::beginChunk` calls `EventLoop::enter`, which records the thread and opens an entry, so a socket the chunk watches is armed in place rather than queued behind a close from another thread, and `EventLoop::run` only runs the entry it was given and never reopens it, so a `Runtime::stop` that lands while the chunk still runs ends the run instead of being overwritten. A watch of a socket libuv cannot watch, such as one closed before its watch reached the loop, runs its handler once the way a close runs the pending ones. The tests `CApi.StopRacingTheChunkOfARunStringNeverWatchesAClosedSocket` and `EventLoop.AWatchOfAClosedSocketRunsItsHandlerOnce` guard this.
  - **A host name is never resolved on the loop thread.** The `socket` module looks a name up on the I/O pool and continues on the loop (`PocoSocketResolver`), and only a numeric address is used in place, since a resolver that answers slowly would hold a whole frame.
  - **A socket of the `socket` module binds exclusively.** A listener binds without `SO_REUSEPORT` unless its caller sets `reusePort`, with `SO_REUSEADDR` on POSIX so a restarted program binds a port in `TIME_WAIT`, and with `SO_EXCLUSIVEADDRUSE` on Windows, where `SO_REUSEADDR` would let another socket take the port over. A UDP socket binds with neither reuse option, since on Linux either lets a second socket share a busy port. A busy port fails with its address.
  - **A closed socket settles what waits on it with the close.** A socket or listener is marked closed before its close runs the pending handlers, and each handler checks the mark before any I/O, so a pending operation rejects with `The socket was closed.` or `The listener was closed.` rather than with whatever the closed descriptor answers, while the empty string stays the end of a stream the peer closed.
  - **A runtime runs as many chunks as the host asks it to.** Per-chunk state (`unhandledError`, `entryRequestedStop`) is reset in `Runtime::beginChunk` before each one, and tearing down the io state belongs to `~Runtime`, never to `EventLoop::run` — a `run()` that clears the poller closes the uv loop and makes every later chunk a silent no-op that still reports success. The test `tests/cpp/runtime-lifetime-test.cpp` guards this.
  - The loop's keep-alive count lives on the `EventLoop` and is changed under the same mutex the idle-exit decision is taken under, so a `varn_runtime_retain` from another thread can never be read after the loop has already decided to exit. Releasing what was never retained is refused rather than driving the count negative, which would leave the loop unable to ever exit.
  - **A C++ exception must never unwind through a platform frame.** The Apple driver catches every exception inside the delegate methods of its session and records it as the failure the transport ends with, and the Android sink turns a throw into the Java exception the transport already handles, since unwinding through an `NSOperationQueue` block or a JNI frame terminates the process.
  - The Apple driver's `.mm` is compiled with `-fobjc-arc` (set per source in `http.cmake`). Without it the session, its delegate, the operation queue and every `NSString` handed to Foundation leak on every request.
  - **JNI hygiene is not optional on Android.** An engine pool thread never returns to Java, so each request runs inside a `PushLocalFrame`/`PopLocalFrame` guard or its local references accumulate until the table overflows and aborts. Every `FindClass`/`GetMethodID`/`GetFieldID` result is checked and named in the failure, and the AAR ships `consumer-rules.pro` so R8 in a consuming app cannot rename what JNI resolves by name — the sample app builds a minified release and CI inspects its dex to prove those rules still hold. Text crosses JNI as UTF-8 bytes (`String(byte[], UTF_8)` and `getBytes(UTF_8)`), never through `NewStringUTF`, whose modified UTF-8 breaks a character outside the basic plane. The library keeps instrumented tests in `android/varn/src/androidTest`, which `./gradlew :varn:connectedDebugAndroidTest` runs on an emulator.
- **Memory crosses the bridge by reference as data views.** The module `dataview` (`modules/dataview/`) is the one way a buffer crosses between Lua and a host without a copy, so a feature that moves large data, such as a camera frame, builds on it instead of adding a pointer of its own. A view is a block of the process registry (`varn::dataview::DataView`, the opaque `varn_dataview` of the C API) with an atomic count of references, an address, a size and an id that is never reused, and the last reference frees the memory or hands wrapped memory back to its owner on the thread that drops it. Lua reads and writes the bytes of a view in place by offset (`view[i]`), which is how a script changes shared memory where `ffi` is absent, such as in the browser. JSON carries only the token `{"$view": id, "pointer": "0x...", "size": n}`, whose pointer is hexadecimal text so a tagged 64-bit address survives every language, and a token resolves only to a live view with that exact id, pointer and size. Only the bridge of the host writes and reads tokens (`JsonSerializer::serializeBridge`, `deserializeBridge` and `acquireViews`), while `json.encode` refuses a view and `json.decode` keeps a token as a plain table, so no address reaches the network and no JSON from the network reaches memory. Whoever sends a token keeps the view alive until the call that carries it returns: a host function reads the views of its argument while it runs, `varn_runtime_emit` takes its references when it is called, and `varn_runtime_release_dataview` gives back a view made for an answer once the loop finished the current job. The class `VarnDataView` exists for Objective-C and Swift (`modules/dataview/platform/apple`, compiled into the core on Apple systems), for Java and Kotlin (`android/varn/src/main/java/com/varn/VarnDataView.java`, whose natives `varn::dataview::DataViewJni::publish` registers from the `JNI_OnLoad` of the host) and for JavaScript (`src/wasm/varn-dataview.js`), and an engine that embeds the core reuses those files rather than writing its own.
- **Lua is compiled as C++**, so a Lua `error()` unwinds as a C++ exception caught by `pcall`. A yield instead jumps straight back to its `lua_resume` with `_longjmp`, through the header `cmake/varn-lua-unwind.h` forced into `ldo.c` on every compiler but MSVC and in every build but one under the thread sanitizer, which cannot follow the jump, whose `longjmp` unwinds like an exception and saves too little to be worth a second path. Under MSVC a yield is therefore a C++ exception, so a test that measures the cost of a turn skips there. The wasm build takes the same path on the native exceptions and the native `longjmp` of WebAssembly (`-fwasm-exceptions` with `-sSUPPORT_LONGJMP=wasm`), which the Asyncify transform cannot carry, so nothing in the browser build may sleep inside a call. A `std::bad_alloc` that escapes a native function fails as `LUA_ERRMEM`, the way Lua itself runs out of memory. Any other exception is caught in the native function that calls what throws it and raised as a Lua error with its sentence, since Lua takes whatever value tops the stack as the error of an exception it does not know. The function `varnRunChunk` is JavaScript (`src/wasm/varn-wasm-post.js`) that pumps the runtime from the event loop of the page through `varnPollBudget` instead. Every line Lua prints reaches JavaScript the moment it is printed (`varn_wasm_print`), so `varnRunChunk(source, { onPrint })` shows a chunk as it runs, and the playground worker posts each line to the page.
- **A yield runs no destructor.** No C++ function keeps a destructible local (a string, a container, a smart pointer, a lock) alive across `lua_callk`, `lua_pcallk` or `lua_yieldk`, and none makes those calls from inside a `catch` block. Scope such locals in a block that closes before the call and carry what the continuation needs on the Lua stack or in its `lua_KContext`, the way `HttpApp::corsMiddleware` and `AsyncModule::entryBody` do. The rule is documented for embedders in [docs/embedding.md](docs/embedding.md), and `tests/cpp/lua-unwind-test.cpp` guards the cost and the semantics.
- **Components live in their own repository**, [varn-org/components](https://github.com/varn-org/components). They are pure Lua on top of the modules and need only a released `varn` binary, so they never enter this build. A change to a module's Lua-facing API can break them, and that repository's CI is what catches it — it tests against a released engine and re-runs weekly.
- **Targets** (`-DVARN_TARGET=`) are `cli` (desktop executable), `wasm` (browser), `port` (the static core alone for a host that ports Varn to a system it does not know: every driver the host does not name is the one that needs nothing of the system, TLS is off unless the host turns it on, the event loop is `PUMP`, whose pools keep their threads unless `VARN_THREADS` is off, and Lua builds as the Lua of standard C where Varn does not know the system), `apple` (`varn.xcframework`), `android` (`aar`), and `lib` (an embeddable shared library exporting only the C API, installed as a `find_package(varn)` → `varn::varn` package). The same Lua script runs on all of them.
- **Embedding**: The C ABI is `modules/api/include/varn/varn.h` (`varn_runtime_new`/`new_with_options`/`register`/`emit`/`retain`/`release`/`run_file`/`run_string`/`load_file`/`load_string`/`poll`/`poll_budget`/`set_wake`/`idle`/`stop`/`free`/`release_dataview`, `varn_version`, and the `varn_dataview_*` functions of data views). The bridge runs both ways. The function `varn_runtime_register` exposes a native function to Lua under the global `host` table, and `varn_runtime_emit` delivers an event from any thread to the handlers a script registered with `host.on`. The functions `varn_runtime_retain`/`release` hold the loop open so a runtime can wait for events instead of exiting once its chunk returns. Everything is marshalled through JSON, so a host app drives Varn (and reaches native capabilities like UI) without touching Lua types. The command `python3 varn.py lib --prefix <dir> --install` builds and installs the package. The shared library exports only the C API (a linker script hides every statically linked dependency). An engine that links the static core adds its native modules with `Runtime::addModule` and its statically linked symbols for `ffi.C` with `Runtime::addSymbol`, both refusing a name already taken, sends HTTP requests with `varn::http::client::HttpClient` on its scheduler, and learns of every failure no caller receives through the one handler of `async.onFailure`. See [docs/embedding.md](docs/embedding.md) and [examples/embedding](examples/embedding).

## C++ style and formatting

Match the existing visual, structural, and architectural pattern. Compact, professional, consistent. The `clang-format` configuration is LLVM-based with **Allman braces** (run `python3 varn.py format`).

- Avoid excess vertical space. Use only the blank lines needed to separate reading contexts. **Separate blocks of different responsibility with one blank line.**
- Never leave multiple `if`s, validations, loops, state mutations, and returns visually glued together. A function must read with an identifiable beginning, middle, and end at a glance.
- Prefer early returns. Avoid unnecessary nesting. **No unnecessary `else` after a `return`.**
- Extract a function only when one is doing too much — never to shrink size or for artificial abstraction that hides the main flow.
- Keep includes clean, direct, organized. Keep headers, implementation, namespaces, types, names, and responsibilities consistent.
- Prefer `const`, references, and smart pointers for clarity, safety, and ownership. Avoid macros, unsafe casts, and raw owning pointers when a safer project-consistent alternative exists.
- **No free functions anywhere — group helpers as `static` methods of a class** (like `varn::lua::LuaHelpers`). Even a file-local helper is a `static` method of a file-local class declared inside the anonymous namespace, never a bare function floating in the namespace. The only exception is the C-ABI interop functions that must stay `extern "C"` and free.
- **Do not put comments in headers describing methods, sections, or members.**
- **Lambdas: clang-format mangles C++ lambdas, so wrap each non-trivial lambda region in `// clang-format off` … `// clang-format on` and hand-format it cleanly.** Those markers belong to C and C++ only, since `format` runs `clang-format` over `modules/` and `src/` and never reaches the Swift or Kotlin an app is written in.
- **TLS runs on OpenSSL on every platform, Windows included.** Poco is built with `NetSSL` and never with `NetSSL_Win`, so the HTTP server, the desktop HTTP client and the `socket` module serve and verify certificates the same way everywhere and read PEM files directly. A client context verifies against the trust store of the system through `varn::tls::SystemTrust::install`, since the bundled OpenSSL ships none, which loads the bundle `varn::tls::CaBundle` finds on POSIX and copies the root store of Windows in.

## Comments

- **Every comment is a complete sentence and ends with a full stop.**
- **A comment above a function, method, class or module says what it does for the caller, never how it is implemented inside.**
- **Never break one sentence across lines, and never continue a sentence on the next line.** If you need a second sentence, close the first with a full stop and start the next on its own line.
- Comments are objective and natural. Nothing verbose, fragmented or narrative, no decorative banners like `helpers` or `public methods`, and no historical or before/after framing.
- **Comment in the `.cpp`, not in the `.h`, and only where it genuinely earns its place.** A header carries declarations, not prose.
- A comment explains intent or context. It never restates what the code literally does, and usage examples belong in the docs.
- Code and comments are in English.

## The Lua-facing API

- Anything reachable from Lua is a contract with [varn-org/components](https://github.com/varn-org/components) and with anyone else building on the engine. Changing a signature there is a breaking change even when nothing in this repository fails, so it belongs in a major version and the components repository is told before it ships.
- The field `platform.version` carries `{ major, minor, patch, string }` so a caller can gate on the engine it needs without parsing the string.

## Testing and docs

- Each capability has runnable examples and individual Lua tests. CI runs `modules/*/lua/tests` and the C++ targets `varn-tests` and `varn-scheduler-tests` on Windows/Linux/macOS, and the Lua tests are auto-discovered from the tree. A test that needs what Lua cannot make, such as a certificate for a TLS server, belongs in the C++ target so it still runs on every desktop platform.
- **Check `git status` before finishing.** The `.gitignore` patterns for build and environment directories are anchored to the repository root (`/env/`, not `env/`) precisely so they cannot swallow a source directory that happens to share the name. A new module or component that does not appear as untracked in `git status` is being ignored, not committed.
- Each build workflow cancels its own superseded runs through a `concurrency` group. The group name is a **literal per file** (`build-linux-${{ github.ref }}`), never `${{ github.workflow }}` — `release.yml` calls every build workflow as a reusable workflow, where that context resolves to the caller's name, so they would share one group and cancel each other mid-release. A tag carries its own ref, so a release is never cancelled by a push to main.
- **Every compile of CI goes through sccache with the Cloudflare R2 bucket `varn-ci`.** The action `.github/actions/build-environment` installs sccache and sets the launchers of CMake, and the workflows hand it the secrets `VARN_R2_ENDPOINT`, `VARN_R2_KEY_ID` and `VARN_R2_SECRET`, so every push and branch of the repository reads and writes the cache while a pull request from a fork compiles without it. The bucket keeps one layer under each prefix, the objects of sccache under `sccache/`, the sources of the dependencies, their prebuilt packages and what Gradle downloads under `dependencies/` and the SDK of Emscripten under `tools/`, never in the cache of GitHub, as archives under keys of everything their contents depend on that the action `.github/actions/caches` saves at the end of the job that saves each one, so no workflow caches a build tree. OpenSSL, which builds with a build system of its own, keeps each build as a prebuilt package in the folder that `VARN_PACKAGE_CACHE` names, under the hash of everything the build depends on, so a tree whose hash matches takes the package instead of building OpenSSL. The action sets `CMAKE_BUILD_PARALLEL_LEVEL` to the processors of the runner, so OpenSSL builds with as many jobs as the rest, and every job ends with the report of `.github/actions/compiler-cache`, which says how many of its compiles came from the cache. The Apple workflow builds the slices in one job per family of `tools/core/targets/apple.py` and assembles the XCFramework in a job of its own. [docs/build.md](docs/build.md#-continuous-integration) describes it.
- CI gates on Linux with **ASan + UBSan** and LeakSanitizer (`detect_leaks=1`) over the whole Lua suite and the C++ targets, and with **TSan** over the C++ targets — the Lua suite is not run under TSan because forking under it is pathologically slow. A concurrency fix therefore belongs in `tests/cpp/` or `tests/scheduler/` where TSan will see it. A leak is fixed at its owner, and a suppression file is only ever for a leak inside a third-party library that cannot be fixed, documented beside the entry that suppresses it. Memory a module keeps for as long as its Lua state lives is owned by that state, the way the parser of `ffi` keeps its types in registry userdata, so closing the state releases it.
- The WebAssembly engine is tested in Node.js by `tests/wasm/varn-wasm-test.mjs`, which the wasm workflow runs after the build, so the native exceptions, the yields and the pump of the page are checked on every change.
- Native unit tests are plain googletest in `tests/cpp/*.cpp` (auto-globbed into `varn-tests`, which links `varn-core`) and in `tests/scheduler/` (`varn-scheduler-tests`, which links only `varn-runtime`, so a test of the scheduler, the log, data views or the HTTP client that needs no Lua belongs there). The include dirs of `varn-tests` let a test reach a module's internal headers. Concurrency and internal-state invariants (`WorkLedger`, `TaskPool`, `EventLoop`) are exercised with multi-threaded stress tests in both.
- **Prose in Markdown is never hard-wrapped.** One paragraph is one line, however long it runs, and a list item is one line with its continuation folded in. Never break a sentence across lines — a sentence that starts mid-line in the source is the defect this rule exists to prevent. Tables, fenced code and indented code keep their own line structure.
- **The product is `Varn` in prose** even though the binary, the library and the header directory are all `varn`, so a sentence opening on the product name is written `Varn`.
- **No `;` splitting clauses in documentation either.** Two independent clauses are two sentences. The file `LICENSE.md` is exempt from every rule here and is never reformatted, since its text is legally verbatim, and so are the GitHub issue templates, whose front matter and field layout are structure rather than prose.
- Docs are two-tier, and **both tiers exist for every module**. Tier one is the `README.md` next to the code: a short intro, a capabilities table, and a closing `## Reference and tests` section linking the reference page and `lua/tests/`. Tier two is the full reference under `docs/lua-api/<module>.md` — the complete API plus a runnable example of every capability, which lives only there since the module tree carries no examples of its own. The page `docs/lua-api.md` indexes them, and every row of that table points at a `docs/` page, never at a `README.md`. Adding a module means adding its reference page and its index row in the same change.
- The page `docs/roadmap.md` records what is covered and what is genuinely still open. Closing a gap means moving it into "Already covered" in the same change — a roadmap that lists shipped features as missing is worse than no roadmap.
- The main `README.md` is presentation only. Keep docs objective and present-tense.
